头条：Claude Opus 5.5 发布、数据与反响

发生了什么

Anthropic 发布了 Claude Opus 5.5，这是全新 Claude 5.5 家族的首个模型。其卖点是以 Opus 的价格提供 Fable 5.1 级别的能力，速度更快、写作更好。OpenAI 在大约一小时后发布了 GPT-6 Sol 和 Luna。

  • 发布声明。Opus 5.5“在大多数任务上的表现达到 Claude Fable 5.1 的水平，运行成本比 Opus 5 低 40%”（@claudeai；@AnthropicAI）。

  • 领先之处。Anthropic 称其在 agentic coding、computer use 和知识工作上领先（@claudeai）。

  • 速度与成本。它比 Opus 5 快约 30%，每任务成本低约 40%（@ClaudeDevs，@lydiahallie）。

  • 沟通改进。该模型把最重要的信息放在前面，并遵循用户的写作规则。这针对的是对 Opus 5 最常见的反馈（@claudeai）。

  • 订阅变更：

    • 5 小时会话限额提高 20%。

    • 价格下调意味着限额可多用 25%。

    • Pro、Max 和 Team 用户可获得一次可存储的速率限制重置，随时自行使用（@claudeai、@ClaudeDevs、@trq212）。

  • 新默认设置。 Opus 5.5 现已成为 Claude Code 和 Claude 应用（包括 Cowork）的默认模型。默认 effort 为 medium，被描述为“智能水平与 Fable 5.1 相当，但速度更快”（@_catwu）。

  • 可用性。 它已在 Claude Code 和 Claude Platform API 中上线（@ClaudeDevs），也已在 Slack 版 Claude Tag 中上线（@_catwu）。

  • 路线图。 Sonnet 5.5 和 Haiku 5.5 将“在未来几周内”跟进（@mikeyk、@AiBattle_）。这与 Haiku 已停产的传闻相矛盾（@kimmonismus）。

  • 保障措施。 Opus 5.5 是首个在网络、生物和前沿 LLM 开发方面具备 Fable 5.1 级保障的 Opus 模型。被标记的请求会回退到另一个模型，Anthropic 表示正在“努力减少错误标记”（@ClaudeDevs）。

  • 发布前信号。 该模型在公告发布前不久已在 Claude Code 中被发现（@kimmonismus）。

  • 系统卡。 已在发布时公布（@scaling01）。

定价与 token 经济性（事实）

  • 标价。 Token 定价下调 20%，从每 100 万输入/输出 token 5 美元/25 美元降至 4 美元/20 美元（@ValsAI）。

  • 被更高的 token 用量抵消。 Vals 指出，Opus 5.5 通常使用更多 token，尤其是在编程方面，而它在该领域提升最大。更低的名义价格被用量部分抵消。

  • Artificial Analysis 成本拆解。 在 max effort 下，Opus 5.5 每项 Intelligence Index 任务成本为 5.98 美元，而 Opus 5（max）为 5.86 美元。他们的拆解如下（@ArtificialAnlys）：

    • 仅更高的 token 用量就会使每项任务成本提高约 80%，达到 10.51 美元。

    • 基础价格下调 20% 后降至 8.41 美元。

    • 更便宜的缓存读取（0.20 美元）使其降至 5.98 美元。

  • 这意味着什么。 在 max effort 下，相比 Opus 5 的每任务节省消失了。“便宜 40%”的说法适用于默认（medium）设置。

  • 相对于 Fable 5.1。 Cline 报告称，Opus 5.5 在 Artificial Analysis Intelligence Index 上击败 Fable 5.1，成本约低 2.5 倍（@cline）。

  • Prompt 缓存。 在 Claude Code v2.1.280+ 上，会话中途切换 effort 不会破坏 prompt 缓存（@lydiahallie）。

  • 模型规模（推测）。 @theo 声称 Opus 5.5 比 Opus 5 更小，并将此归功于后训练。官方帖子未证实这一点。

  • 结果就是，模型“在更高的推理 effort 下表现反而持续变差”。

系统卡细节

  • 多 agent 扩展。 系统卡在第 8.12 节中报告了最多 100 个并行 agent 的扩展。 @scaling01 称这是同类中首份实验室报告。 @maksym_andr 将其作为多 agent 扩展定律的证据加以强调。

  • ProgramBench 的注意事项。 ProgramBench 作者 @OfirPress 指出，Anthropic 接近 100% 的解决率来自一个 166/200 的子集。该子集很可能排除了最难的程序，例如 FFmpeg 和 PHP 编译器。他还指出了指标不匹配的问题（@OfirPress、@OfirPress）：

    • Anthropic 报告的是平均测试通过率。

    • ProgramBench 报告的是完整任务完成情况。

    • 部分解决往往能通过 60–70% 的测试，这会抬高通过率指标。

  • 与 Mythos 5.1 的对比。 Opus 5.5 在 Anthropic 的 ECI 上得分高于 Mythos 5.1，并在所有测试过的网络评估中击败了它（@scaling01、@scaling01）。

  • 奇怪的失准发现。 @teortaxesTex 引用了一段话：恶意输出“几乎只出现在以下情况中，即在恶意输出之前，Claude 犯了一个不太可能发生的、无害的错误。”他问 Anthropic 是不是“把自己变成了潜伏 agent”。

  • “从 RSI 训练而来。” 他另外引用了一句关于“首个从 RSI 训练而来的模型”的话，并称其令人担忧（@teortaxesTex）。

  • 生物医学成像。 @iScienceLuvr 对报告中提到的生物医学图像分析能力表示欢迎。

  • 要求提供更多信息。 @scaling01 要求提供不带 chain-of-thought 的时间跨度。

OpenAI 的 GPT-6 Sol 和 Luna：面向 Codex、Work 和 API 的更便宜、源自 Astra 的模型

  • OpenAI 在数小时内以 GPT-6 Sol 和 GPT-6 Luna 作出回应，称其为更快、更便宜的模型，继承了 GPT-6 Astra 在编程、计算机使用、事实性和对齐方面的诸多进步 @OpenAI @OpenAIDevs。定价极具攻击性：Sol 为每百万输入/输出 token 2 美元 / 10 美元，Luna 为 0.10 美元 / 0.50 美元，各自比其 GPT-5.6 前代便宜约 50% @OpenAI。它们已上线 ChatGPT Work 和 Codex 以及 API，其中 Luna 还面向桌面应用中的 Free 和 Go 用户开放，但值得注意的是尚未在 Chat 模式中提供 @OpenAI。

  • OpenAI 的对比框架侧重于每任务成本的帕累托改进，而非绝对的旗舰前沿胜利。其公布的示例声称，Sol 在 xhigh effort 下于 AutomationBench 上击败 Claude Opus 5 max，每任务成本约为后者的 9%；而 Luna max 在 OSWorld 2.0 离线测试中超过 GPT-5.6 Sol medium，成本仅为后者的十分之一 @reach_vb。第三方集成迅速跟进：Perplexity 将 Sol 设为其默认的“Light” effort 编排器 @perplexity_ai，Devin 报告称 Sol 在每任务成本低 61% 的情况下与 GPT-5.6 Sol 持平，Luna 则以约四分之一成本击败其前代 @cognition，Arena 则将两者加入 agentic 和代码侧测试 @arena。

  • 更深层的基础设施故事可能比 SKU 名称更重要。OpenAI 表示其改进了缓存与推理效率，对缓存输入 token 读取提供最高 90% 的折扣，并推出新的 Prompt Caching Dashboard 以及诊断 API，用于理解缓存复用失效的原因 @OpenAIDevs @OpenAIDevs。这对长时间运行的 agent 尤其重要——工具开关或推理变化导致的缓存失效一直代价高昂。市场反应不一：许多人称赞其经济性，尤其是 Luna 的价格下限，而另一些人则认为 Anthropic 在头部模型质量上胜出，OpenAI 则在可负担性和部署易用性上取胜 @kimmonismus @synthwavedd。

Agent 基础设施、Eval 工具与基于真实使用的后训练

  • 多篇帖子都指向一个如今已不陌生的模式：价值正从原始模型访问转向harness、evals、路由，以及基于专有轨迹的后训练。DigitalOcean Managed Agents 进入公开预览，支持 Claude Code、Codex 和 LangGraph 风格的 agent，并提供空闲时暂停的运行时、受治理的工具端点，以及 75+ 种模型选择 @digitalocean。在开发者工作流方面，VS Code Agent Merge 推出了一项实验性模式，可在 PR 内自动解决评审意见、失败的检查和合并冲突 @code。

  • Perplexity 分享了较为具体的后训练报告之一：其 Computer agent 在真实用户会话上混合使用拒绝采样微调与提示引导的自蒸馏，从成功轨迹和明确的工具调用错误中学习，并声称在线上 A/B 测试中工具调用失败率降低了 21.2% @perplexity_ai @AravSrinivas。这是一个有用的例子，说明实验室如何通过生产轨迹而非纯合成的 RL 环境，将仿真到现实的桥接付诸实践。

  • Eval 与可观测性工具也受到关注。Lenny 的 newsletter 重点介绍了 Ramp、Shopify、Harvey 和 Cursor 等公司在 eval 投入上的具体 ROI，并链接了 Hamel Husain 与 Shreya Shankar 关于高级 eval 系统的续作 @lennysan。Hamel 还发布了一个 evals 技能/插件，旨在自动化部分 eval 审计和错误分析工作 @lennysan。在可观测性方面，LangSmith 发布了对 Jev/SemIf 等决策模型的改进支持，使状态、问题、选择和输出在 agent 轨迹中更易于检查 @hwchase17 @LangChain。多位实践者的元观点是：即使模型和 prompt 相同，harness 也可能实质性改变 benchmark 结果 @omarsar0。

开放模型、压缩，以及在更小硬件上运行更大模型的系统工作

  • Tim Dettmers 以一场“开源周”拉开序幕，推出了集成到 bitsandbytes2 中的运行时动态压缩框架，目标是在高质量下实现 1.5–2.0 bit 压缩，并承诺“惰性压缩”能在部署时自动找到更优的内存/质量/速度权衡 @Tim_Dettmers @Tim_Dettmers。这一构想明确面向那些试图在内存受限（包括不断增长的 KV 缓存）的情况下运行大型开放权重模型的小团队和个人。

  • 硬件与本地部署是另一个主题。一篇关于 NVIDIA DGX Spark 的上手文章描述了一台 15×15×5.05 cm、重 1.2 kg 的系统，搭载 GB10 Grace Blackwell、128 GB 统一内存，以及最高 1 PFLOP FP4 稀疏理论算力；NVIDIA 声称其支持对最高 200B 参数的模型进行本地推理（配合量化），并可通过 QLoRA 等方法对最高 70B 的模型进行微调 @kimmonismus。另外，Reka EdgeQ 展示了一款直接针对高通 Hexagon NPU 优化的端侧 VLM，TTFT 为 0.73s、每次推理 6.9 mWh，并让 GPU 保持空闲以实现持续的热性能 @RekaAILabs。

  • 在开放模型方面，有几项有意义的发布，而不仅仅是评论。Step Code v0.1.0 以 MIT 许可发布，打包了一个编码 agent CLI，据报告在 Terminal-Bench 2.1 上得分 80.9%，在包含 150 项任务的长时程 benchmark Multi-Frame 上得分 73.3% @StepFun_ai。Ming-Image-0.1-Design 是一个 6B 开放权重图像设计系列，随 UI 设计和图像转可编辑 PPT 的“agent skills”一同发布，声称在 Artificial Analysis 的 UI/UX 设计排行榜上位列开放权重模型第一 @AntLingAGI。一项规模较小但技术上值得关注的预训练成果来自 Rigel，这是一个 2.3B MoE / 360M 激活的 Hybrid Mamba-2，据报道在单一代码库上跨 H100/A100/V100 与 TPU v5p/v6e 混合硬件训练，仅用 Llama-3.2-3B <1% 的预训练 FLOPs 就达到了与其相差几个百分点的水平 @MayankMish98。
