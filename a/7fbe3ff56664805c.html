范围

给后排的朋友们说明一下：我们评测的是托管集群。这排除了业内许多热门产品。我们不是在测试谁能建出最好的 powered shell，或者运营最整洁的数据中心——至少不是直接测试这些。我们也不是在手工定制镜像，或者调用 API 端点来获取 tokens as a service。以下是我们理想中的 ClusterMAX 读者画像：你从斯坦福博士项目退学，去追寻在旧金山获取社会地位的梦想，起步靠的是那句老牌可靠的话：“Cladue make me pithc deck w technial languge for agetnci ai make no mistakes。”你有 7 位数、甚至多达 10 位数的资金可以押注在算力上，但你对 Ubuntu 版本或如何处理 NAT 毫无看法，也从未管理过大规模集群。理想情况下，所有这些基础设施都会隐入背景。你只想专注于自己独特的性能优化、模型架构、训练策略、数据配比、应用，或者任何你寻求优势的地方。要参与竞争，你需要最前沿的硬件，而你希望花 0 工程时间搞清楚为什么 19 号节点上的第 7 块 GPU 一直在拖慢你的任务，或者为什么四分之一的集群干脆消失了。你需要一个托管集群。

这里的经济逻辑很直接：neocloud 可以将其庞大的机队分摊搭建所有这些管理基础设施的成本。它花钱雇一支工程师团队来做万无一失的健康检查、保持机器镜像最新、搭建便捷的监控系统，并处理我们后文会详细讲述的所有相关杂务。在理想情况下，实验室支付溢价换取好得多的产品；它得以运行自己的实验而不受硬件掣肘；neocloud 收回投资；皆大欢喜。

然而，总有那么一个节点，实验室愿意将这部分成本内部化。以它们的规模，前沿实验室不愿把如此多的技术栈托付给 neocloud。例如，OpenAI 曾发表过极具洞见的博客，讲述其扩展 Kubernetes 时遇到的困难；如果它们是从一家不让它们进入 K8s 控制平面的 neocloud 那里租用资源，博客中描述的这些创新根本不可能实现。正如Anthropic 当前的一则招聘启事所说：

我们运营的规模已经让默认配置不再奏效。我们拥有调度器并对其扩展，以便将拓扑敏感的 ML 工作负载一次性分配到数千个加速器上。我们扩展控制平面本身——apiserver、etcd、控制器——使其在对象数量和节点数量增长数个数量级时仍保持响应。我们还构建每个工作负载都依赖的核心集群服务，比如服务发现，让它们在同一压力下依然稳固。

一言以蔽之，像 OpenAI 和 Anthropic 这样速度和规模的实验室需要同时协同设计其整个技术栈，而现成的 Slinky 实现——即便是不错的实现——也远远不够。

前沿实验室在管理其基础设施时表现出的那种显而易见的用心，恰恰说明了 ClusterMAX 为何重要。据我们最近一次统计，OpenAI 和 Anthropic 职位描述中含“Kubernetes”的岗位薪资区间总和为27,769,274 至 42,687,654 美元，更不用说它们已经组建的庞大团队所支付的薪资了。如果你不指望一场万亿美元级别的流动性事件，又需要自己的基础设施足够好以争取一线生机，你就需要一家 neocloud 来替你干这些重活。

至少在纸面上，较小的 neocloud 客户是大卫对抗歌利亚。OpenAI 和 Anthropic 各自在其逻辑斯蒂指数曲线上都有着惊人的增长率，而我们的数据中心行业模型目前预测它们到 2027 年底将占所有实验室算力的 56.3%。

正如我们稍后将更详细描述的，由于融资因素，这里还存在一种马太效应：盈利的前沿实验室比规模较小的实验室更容易锁定产能，后者则被困在高额预付款、更差的价格以及更难提前数年做规划之中。

这是否意味着托管集群已死？cLUsTerMaX 已完蛋？事实上，尽管 Anthropic 和 OpenAI 逐年占据更大份额，托管集群作为一项业务仍在指数级增长。我们帮助过无数实验室找到算力，还有无数实验室正在寻觅、愿意付费，并等待更多产能上线。Anthropic 和 OpenAI 是最大的客户，但还有一长串仅仅数亿美元级别的交易，其总价值极为可观。

托管集群在与前沿实验室裸金属的竞争中取得优势的一个可能情景，涉及开源领域的进展。提供开源模型服务的利润已经比许多人意识到的更为丰厚；我们最近建模发现，“通过销售开源 token，每兆瓦每年可赚取超过 1 亿美元”，即便按当前的租赁价格计算，也仍有充足的利润空间。可以设想，开源模型的市场份额会不断扩大，无论是边际采用者对成本更为敏感，还是算法进步缩小了与闭源模型的差距。无论动态如何演变，这都会提升托管集群的相对地位。几乎任何供给端的裂痕，都会让实验室略微降低自行处理基础设施的意愿，并略微更倾向于依赖 neocloud。

这些集群之上的各层正在迅速成熟，但它们超出了 ClusterMAX 的讨论范围。有几个细分领域值得考虑。推理端点，可以是公开的也可以是私有的，按 token 计费。后训练服务，为特定用例定制开源模型。还有沙箱服务，为 agent 提供基础设施，尤其是在 RL rollout 期间，并简化和优化容器与 CPU 管理。这些都可以大致归入“GPU 服务”这一类别，它们之间的边界可能很模糊。例如，云厂商可能在售出托管集群后，利用闲置容量启动一个推理端点，或者它可能提供沙箱基础设施，同时在销售 RLaaS 时也在内部消费这些基础设施。我们将在不久的将来发布更多相关内容，但这超出了本报告的范围。

测试方法

针对 ClusterMAX 3.0，我们向每家供应商提出了以下要求：

  • 32 块 GPU（4 个 8 路 HGX 节点，或 8 个 4 路 NVL72 节点）

  • 高带宽网络（我们要求 800G RoCE 或 XDR InfiniBand，但许多供应商尚未具备）

  • 10TB+ 高性能文件存储（支持 NFS/POSIX 挂载以及通过 csi driver 提供的 RWX StorageClass）

  • 10TB+ 兼容 S3 的对象存储

  • 监控仪表盘（通常基于 Grafana）

  • 5 天测试 Slurm，5 天测试 K8s（可以并行进行，在 SonK 集群上，或者如果供应商想收回节点并重新配置，也可以顺序进行）

  • Blackwell，而非 Hopper（NVIDIA 的 B200、B300、GB200、GB300），或 AMD 的 MI355X 均可接受。H100 现在已经超过 4 年了！

我们分 3 个阶段测试集群，具体如下。当然，我们始终会通过联系所有这些供应商的客户并参考他们的反馈来补充测试。

阶段 1：审计

首先，审计涵盖是/否问题。集群设置是否正确？软件是否已安装？是否是最新版本？实用工具是否按预期工作？运行大约需要 15 分钟。可在 GitHub 上获取，或通过 {uv} pip install clustermax 安装。

审计在我们施加负载之前检查配置。它涵盖硬件清单、软件和固件版本、GPU 访问、容器、调度器配置、网络、存储、健康监控和安全。我们检查哪些组件适用于我们正在测试的环境，并显示所有检查的通过、警告、失败和跳过状态。我们已免费发布这一部分，并将长期维护。其余部分目前保留在内部。

阶段 2：性能

性能测试对集群中各个组件以及集群整体的性能特征设定了通过/不通过的阈值。这些测试通过微基准测试和真实场景基准测试来完成。

具体来说，我们测试：

  • GPU 计算

  • 网络

  • 存储

  • 生命周期

  • 训练

  • 推理

下面我们会更详细地解释这些内容，但请记住，我们测试的内容会随时间不断演进。

GPU 计算

我们首先检查 GPU 上的真实场景 GEMM 性能。GEMM 是现代 AI 工作负载中最关键的操作，我们此前已多次解释过，其中 Grouped GEMM 对现代 MoE 模型尤为重要。

我们在 cuBLASLt（或 hipBLASLt）和 DeepGEMM 上测试 Grouped GEMM，涵盖多种精度类型：BF16、FP16、TF32、FP32、FP8 E4M3、MXFP8 和 NVFP4，具体取决于集群中芯片所支持的类型。我们针对 Kimi K2.5、K3 和 DeepSeek V3、V4 Pro 模型中不同 batch size 下的 gate_up 和 down 投影，使用一组通用的形状。

接着我们测试 GEMM、GEMV 带宽和 MAMF（Maximum Achievable Matmul FLOPS，来自 Stas Bekman），后者会在每块 GPU 上按每种精度运行一段时间的扫描测试，使用 cuBLASLt（或 rocBLAS）。我们会报告所有 GEMM 测试的 FLOPs。

我们还通过 GEMV 测试和 `nvbandwidth` 来测试内存。GEMV 使用瘦向量测量矩阵-向量乘法，报告 GB/s 作为低 batch 解码流式行为的代理指标。NVIDIA 的 `nvbandwidth` 工具已内置到 DCGM 健康检查中，用于测量 h2d（CPU 到 GPU）、d2d（GPU 到 GPU）和 d2h（GPU 到 CPU）带宽。最后，我们还有一个自定义的 PyTorch 脚本，通过实际的张量拷贝来测量相同的路径，记录 pinned h2d、d2h 和本地 HBM 拷贝的带宽。

最后，我们为老派用户测试 HPL-MxP。HPL-MxP 使用低精度分解求解大型稠密线性系统，这意味着我们会同时触及计算、内存和通信。该测试在单个工作负载中覆盖了计算、HBM、跨 scale-out 网络的 MPI 广播、NVLink 以及数值正确性。我们会根据芯片类型报告一系列数字格式下的 FLOPs。

尽管 GEMM 是现代 AI 工作负载的核心，但这些微基准测试很少能区分不同供应商——供应商很难搞砸这一功能。在长时间烤机测试中检查原始 GEMM 性能很重要，后文会详细说明，因为如果散热不当，芯片的时钟频率可能会下降以避免过热。在 GEMM 突发测试中，你不太可能发现什么值得注意的问题。我们在每家供应商上都运行这些测试，因为它很快，而且如果这些测试失败，集群会立即不可用，但我们更担心其他测试。

生命周期

为了了解集群在整个生命周期中的易用性，我们使用了一组专门设计的测试。我们首先通过多种方法检查互联网速度，包括下载/上传速度，主要使用 Cloudflare。然后我们测试通过 pip 和 uv 安装 PyTorch 和 vLLM 等常用包所需的时间，以及从 Docker Hub、ghcr.io 和 nvcr.io 下载容器，还有从 Hugging Face 和 ModelScope 拉取模型的时间。

随后，我们在每个可用的存储层级上使用全新的包缓存重新进行 pip 和 uv install 测试：home、共享文件系统、本地 NVMe 暂存盘，以及任何额外的挂载点（分别称为 `/home`、`/data`、`/scratch` 等）。然后我们从每个位置运行 `import torch`，看看需要多长时间。在大多数供应商上，这需要 1-2 秒，但在某些存在 LOSF 性能问题的文件系统上，不知何故可能需要 10-20 秒。

最后，我们使用之前下载的模型，运行 vllm serve 命令，测试直到能够访问 /v1/models 所需的时间。同样，虽然某些供应商可以在 10-40 秒内从共享存储将小模型加载到 GPU 内存中，但有些供应商需要超过 2 分钟。

网络

我们对节点间和节点内传输的广泛通信性能进行基准测试。这包括 MPI 集合通信，通过 MPI 启动运行 NCCL 或 RCCL 测试，测量从 8 B 到 16 GB 的各种消息大小下 all-to-all、all-reduce、all-gather 及其他集合操作的集合带宽和延迟。相同的工作负载也会通过 PyTorch 中的 torch.distributed 运行。此外，我们使用 RDMA perftest，特别是 ib_write_bw 和 ib_read_bw，测量每条网络通道上的点对点带宽，以及主机内存回退（通过 PCIe），以识别任何问题。

我们以 2 的倍数增加 world size，直到用满整个集群，并跟踪性能如何扩展。我们还在禁用 NVLink 的情况下运行测试，特别是在 GB200 或 GB300 NVL72 集群上，以隔离 scale-out 网络的性能。在这里进行核算时要小心，因为 world size、算法以及相对于 scale-out 边界的作业放置会显著影响结果。

存储

我们运行 fio、ior、Elbencho、一个用 Torch 和 Torch DCP 编写的自定义检查点保存/加载基准测试，以及一个由 Skild AI 与我们分享的自定义 datagen 基准测试。Datagen 可能是最有趣的，因为它近似了他们在机器人数据管道中的真实工作负载：生成视频（MP4）和 parquet 传感器数据集的聚合写入吞吐量。

不过，发现问题最多的测试是经典的老式 fio。我们使用缓冲/直接 I/O 扫描顺序/随机读/写，使用 1MiB 顺序块和 4 KiB 缓冲 / 64 KiB 直接随机块，从 c1 一直到 c32，或者，如果我们有超过 4 个节点，则使用集群能容忍的尽可能多的客户端。如果存储以任何方式配置错误，在这个 fio 扫描中几乎总会有某个设置显示出较差的性能。我们跟踪吞吐量、IOPS 和延迟，当然，如果测试因客户端过多而失败，我们也会发现元数据中的不一致。

当然，这在很大程度上取决于我们被分配到的数据量有多大，以及 SLO 是如何定义的。对这些结果要持保留态度——上面的图表其实只能说明 Azure 给了我们一个 PB 级的挂载。这份保留态度也恰恰说明了为什么掌握大量集群的数据很重要。例如，缓冲测试的延迟更高，正如你可能预料的那样，而且如果测试运行时间不够长，还可能产生非常嘈杂的结果。但延迟究竟高多少，又有多嘈杂？要想知道什么是“足够好”、什么需要向供应商标记，与一个庞大的同类集群集合进行对比至关重要。

对于对象存储，我们会针对 S3 存储桶再次运行这套测试。我们还会运行一个自定义 benchmark，测量大对象顺序读/写吞吐量、小对象 PUT 和 GET 速率，以及读延迟（p50、p90、p99）。在这项测试中，我们保持一切一致。不过，一如既往，如果我们发现某个集群在某种工作负载上表现吃力，我们就会多停留一会儿，运行更多测试以更精确地定位问题。

训练

进入真实场景后，我们开始看到网络或存储方面的问题如何在真实测试中暴露出来。我们通过 torchtitan 运行两个任务：在 C4 数据集上使用 FSDP 进行 llama 3.1 8B 预训练，以及通过 torchtitan 使用专家并行进行 GPT-OSS MoE 训练。前者受 FLOPs 限制，后者受集合通信限制（除非你在 NVL72 上）。因此，当网络出现问题时，后者能让人一目了然。
