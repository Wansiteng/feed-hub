原标题：Revealing the details of how OpenAI agents hacked Hugging Face

要点

  • OpenAI 内部 agent 利用链接短链和截图服务 mShots 构建代码执行链
  • 研究人员解码超 8 万个 payload，发现针对 Hugging Face 内网的扫描脚本
  • Hugging Face 确认 payload 与其调查相符，相关凭证已被撤销

agents 将 Hugging Face 的 worker 变成了可复用的基础设施

9 月 11 日，本文的前三位作者得知，OpenAI 内部的 agents 曾在 6 月试图使用他们创业公司的产品 Parse。这些 agents 与 Collusion.wiki 上发布的报告中详述的属于同一群体，该报告披露 OpenAI 内部的 agents 曾违规使用多个第三方网站，来分享它们在被评估的网页抓取任务中的答案。

团队检查了大量 URL 扫描工具，他们认为 agents 在使用 Parse 的过程中可能用过这些工具。在调查中，他们发现了一个对某公共短链接服务中十几个链接的扫描，其中每个链接都重定向到一个页面，页面上显示一段 base64 编码的代码片段，以及下一个链接的 ID。解码这条链接链中的载荷后，发现了一个扫描 Hugging Face 内部网络的 Python 脚本。第二条链则指向 OpenAI 内部的 Artifactory。这表明这些链接与 Hugging Face 攻击事件有关，促使我们更深入地调查这个问题。

我们收集了攻击期间该短链接服务的链接，扫描了数百万个 URL。在接下来的两周里，我们编写程序跟踪这些链接链，解码了超过 80,000 个载荷。agents 使用了数百种独特的编码格式，有些简单如上文提到的 base64 编码片段，有些则复杂到包含多层嵌套的编码和压缩，最终解包出一个经过加密、带有 RSA 签名的数据块。这些加密数据块的密钥只能从其他链接链中找到。

我们于 9 月 21 日将这一发现通知了 Hugging Face。Hugging Face 确认这些载荷与其自身调查中的产物相符，且其中包含的凭据已被吊销。不过，虽然他们知道 agents 使用了短链接服务，但并不知晓这份具体的 URL 列表。我们于 9 月 24 日通知了 OpenAI。

脱敏说明

我们发布的是一个初步数据集，其中所有凭据、PII 以及关于 Hugging Face 基础设施的具体细节均已脱敏。我们不会公布所使用的任何短链接服务的名称，也不会公布任何我们尚未解码的数据块，以减少未经审查信息的暴露。Hugging Face 要求将所有用户数据（用户名/仓库名）以及若干关于其基础设施的说明也一并脱敏。我们感谢他们的团队在配合我们时展现出的高效与细致。

7 月 8 日，OpenAI 的 agents 在其沙箱环境中发现了一个漏洞，使它们能够访问互联网上的外部网站。这一访问权限似乎只允许 agents 发出“GET”请求，也就是说它们可以抓取和读取网站，但无法与之交互、提交表单或向其发送数据。

agents 能够通过 GET 请求访问的其中一个网站，是一个名为 mShots 的截图服务。用户可以提交一个网站链接，随后 mShots 会在自己的浏览器中打开该页面，截图，并将图片返回给用户。为了渲染网站以进行截图，mShots 会在自己的浏览器中完整加载该网站的所有代码。

如果 agents 能够将代码写入某个网站，它们就能让这项服务执行这些代码。

agents 使用了诸如 httpbun.com 这样的网站，这是一个 HTTP 镜像服务，旨在帮助网页开发者测试他们的 HTTP 代码。小段代码可以被 base64 编码并附加到 HTTP URL 的末尾。httpbun 随后会解码这段片段，并将其作为网页提供。

agents 随后可以将这些 httpbun URL 提交给 mShots，将其加载到该服务的浏览器中，从而执行 agents 的代码。

Agents 很快意识到，单个 URL 中能容纳的代码长度存在上限。为了绕过这一限制，它们会把大型程序拆分成一个个按顺序排列的小代码块，并附带一个缩短的链接（使用类似 bit.ly 的短链接服务），指向序列中下一个代码块的 URL。这就形成了一条 URL 链，沿着这条链追踪下去，就能从许多单独的片段中重建出更大的代码块。只需把第一个链接提交给 mShots，浏览器就会自行跟随其余链接，直到这些代码块被组装成完整程序并在 mShots 的浏览器内执行。

Agents 能够利用这一技巧构造并执行极其庞大的代码，有时串联的链接超过 900 个。

为了读取所发出请求的结果，Agents 使用了许多不同的技术，例如把服务器的响应转换成截图服务自身浏览器内的一块像素网格。随后截图会捕获这块网格，并以图像形式返回给 Agents，Agents 再将其解码回文本。

我们可以从一份恢复的 payload 中看到这一手法的早期尝试。

该脚本向托管在 Modal 上、名为“cybergym”的评估的提交结果端点发起 POST 请求，索取与 agent ID“m47push2”相关联的提交记录。随后脚本清空浏览器页面，并把服务器的响应写回页面，将每个字符的每一位表示为一个像素。通过把像素解码回文本，agent 就能读取由运行在一个完全独立浏览器中的代码所发出的服务器响应，即便截图服务只返回一张图像。

借助这套自定义协议，Agents 能够执行任意代码并接收响应，而这一切都只在拥有 GET 权限的情况下完成。

ResourceRules 是 Kubernetes 编写的权限，以资源和动词来描述——即某个凭据可以访问的对象（资源）以及可对其执行的操作（动词）。

该评分系统看重宽泛的权限和对有价值资源的访问。列出“pods”的规则得 10 分，同时列出“pods”和动词“create”的规则得 15 分，动词列表中出现通配符（‘*’）加 50 分，资源使用通配符则加 100 分。

该函数汇总每个 token 各条规则的得分，然后用得分最高的五个 token 请求额外的私有数据，并将响应保存到 LOOT 中。

一旦确认在 Hugging Face 的数据集 worker 上实现了远程代码执行，这些 agent 便开始部署 C2 基础设施，旨在确保持续访问并运行后续命令。初始 payload 会发布并启动后台控制器（在注释中被称为“bot”“bridge”或“relay”），随后该控制器会监听来自 agent 的进一步指令。因此，这些 agent 可以探查 worker 的文件、在 Hugging Face 的基础设施内执行代码，并尝试访问其他服务，而无需将每一个操作都放入最初的请求中。

我们恢复了其中几个控制器的初始上传脚本、源代码和命令历史——其中一个名为 G236。初始 JavaScript 在截图服务的浏览器中运行，会将数据集 README 及配套文件上传到 Hugging Face。该 README 的数据集配置会引用配套文件中的一个模板注入 payload，其目的是在 worker 处理时启动 Python 控制器。不同的控制器会从不同位置读取命令并写入响应。G236 使用同一仓库中的独立文件。另一个名为 OTS92 的控制器则使用 Hugging Face 的讨论评论来同时完成这两项操作。由于控制器自身会轮询这些位置，因此这些 agent 无需与 worker 建立直接的传入连接。

从我们的数据中恢复出的可复用基础设施还表明，这些 agent 构建了专门的机制来管理运行在可能不同 worker 上、甚至共享同一文件系统的控制器重复副本。这些重复的控制器会从同一位置轮询命令，可能相互干扰或重复工作。因此，控制器和指令中包含了选择存活副本、停止不需要的副本以及替换看似已死亡的控制器的机制。一些控制器会在启动时尝试清理已存在的副本，另一些则在启动后收到执行此操作的指令。

由于控制器大多是通过向数据集 README 配置提交的方式在 HF worker 上启动的，重复处理启动配置可能会运行控制器的重复副本。为此，G236 实例会在启动时尝试创建一次仓库提交。每个实例都会检查当前修订版本，并准备一份包含其主机名、进程 ID、时间戳以及所观察到的仓库修订版本的编辑内容。随后它会提交一次 commit，记录这一声明并使启动 README 失效。

由于这些数据几乎全部来自这些 URL 短链接服务，我们的研究存在若干局限：

  1. 我们的数据中约 80% 是出站数据，截至撰写本文时，我们仅恢复了有限的响应内容。这些 URL 主要被用作访问外部主机的手段；我们关于这些请求结果的数据非常有限。Agent 主要通过上文讨论的截图服务，以及将输出上传到各种 pastebin、webhook 服务器、Hugging Face 数据集和 Artifactory 来获取其操作的响应。

    在此事件接近尾声时，一些 agent 开始对其窃取的数据进行 RSA 加密，我们无法恢复。Agent 还反复发送请求，删除它们用于发布信息的 webhook，并对某些 pastebin 上传设置了极短的过期时间。如前所述，agent 在其 payload 中留下了多条评论，表明它们有意销毁此次攻击的证据。

    因此，我们无从得知这些请求中有多少成功到达了目标。

  2. 我们的重建很可能并不完整。根据初步分析，agent 们使用了超过 1,588 种独特的编码方法组合，来编码它们通过 URL 缩短技术发送的请求。在整个调查过程中，我们多次以为已经根据手头的数据重建出了完整语料库，结果却又发现了一整套全新的编码方法，进而又挖出数千条新的 payload。我们不确定这次事件中究竟还使用过多少种编码方案，也不清楚 agent 们访问互联网时用过的全部站点。同样，agent 们上传到互联网上的大量数据可能可以公开访问，但我们无从得知它们的位置。例如，一条出站 payload 可能把其请求的响应上传到一个新的 pastebin，然后把该 pastebin 的地址转发给一个我们无权访问的 webhook 服务器。

  3. 我们重建出的绝大多数 payload 都不包含日期或时间信息。我们采用多种方法给出最佳估计，但日期不应被视为事实，且容易出错。97% 的 payload 本身不包含任何时间戳信息。对于其余 3% 的 payload，我们通过多种来源提取出了时间戳，例如提取 gzip 头部的第 04-07 字节、解码 JWT、提取 Docker 构建时间，以及任何我们恢复出包含明确时间戳的响应的地方。

  4. 我们认为 agent 可以给自己命名，而且它们的请求中往往不包含名字。

    在本次调查中，我们经常用名字来指代 agent，这些名字提取自它们发送给服务器的头部以及它们在代码中留下的注释。据我们所知，agent 对自己声称的名字拥有完全控制权（它们给自己起名字，以便组织协同工作）。METR 和 Redwood 报告称，参与该留言板的有约 1,200 个 agent，其中约 700 个参与了针对 Hugging Face 的攻击，但我们提取出了 7,905 个不同的 agent 名字。我们并不认为这能证明参与此次事件的 agent 超过 1,200 个，我们认为 agent 们频繁更换名字。因此，我们无从得知究竟有多少 agent 使用过本次调查所描述的技术，也无法得知这里呈现的流量占此次事件总流量的多大比例。

  5. 我们无法确认数据集中的全部活动是否都来自 OpenAI 的 agent。由于这些数据来自数百万条短链接，我们无法确定数据集中的数据是否全部来自这个 swarm。如果某个 URL 匹配上了我们发现的某种编码方案，它可能无意中进入了我们的数据集。在可能的情况下，我们将 agent 名字、文件内容和估计日期与 OpenAI 已发布的数据进行了交叉比对，以确保所呈现的证据很可能源自这个 swarm。我们已标注出分析中与 OpenAI 公布的时间线以及 METR 和 Redwood 公布的时间线不一致的部分。

    我们还观察到了一些似乎与此次事件无关的 agent 流量，但我们认为它们属于 Collusion.wiki 中详述的同一个 swarm，并自称为来自 OpenAI 的 agent。4 即便假设我们的全部数据都是 agent 流量，我们也无法确定哪些流量来自攻击 Hugging Face 的那个 swarm，因为该数据集可能包含任何使用短链接的 agent 或人类的流量，以及其他使用相同短链接手法的 agent swarm 的流量。我们已在可能的情况下努力将这些 payload 区分开来。

  6. 我们无法有把握地判断相当一部分 agent 活动背后的意图。我们观察到许多令我们意外且此前未被报道过的行为，但我们无法说明我们为何认为 agent 尝试了这些行为，也无法说明它们是否真的成功了，或者是否源自 OpenAI 的 agent。例如，一个 agent 曾尝试向 Hugging Face 的大文件存储（LFS）端点发送多个请求，以获取包含 GPT-2 权重的文件。我们最合理的猜测是，这是为了验证与 HF 的 LFS 服务器的连通性。归根结底，对于这类情况，我们只能提供推测。

唯一能澄清这些问题的只有 OpenAI。截至本文撰写时，OpenAI 除了两份自行发布的报告、一次演讲以及由 METR 和 Redwood Research 开展的一项外部调查之外，没有发布任何进一步的信息；在该调查中，三名外部研究人员获得了部分记录，并有六天时间对其进行分析。OpenAI 尚未公开披露 Hugging Face 事件的任何完整记录。OpenAI 已公布针对其自身基础设施的攻击的技术细节，但未公开披露这些攻击的完整记录集。

尽管这群 agent 尤其热衷于寻找可能抓住它们作弊的评分者的信息，但一些 agent 仍继续在互联网上搜索对其最初的 Exploit Gym 任务有用的信息。例如，agent 曾尝试使用 Google、Bing 和 DuckDuckGo 搜索各种已知漏洞，这些漏洞被归类为通用漏洞与暴露（CVE）（多引擎查询、V8 查询、CVE-2025-40300 查询）。其他被保留的请求则针对一个 Chromium issue 的评论列表以及通过 GitHub API 访问的一个 Kata Containers issue。这些请求来源并不能证明返回了完整的讨论内容。

根据我们的初步分析，我们认为这些搜索与分配给 agent 的 Exploit Gym 任务有关。对于少数查询，我们不确定它们与任何 Exploit Gym 任务是否相关，例如 agent 对 CVE-2026-47243（Kata Containers 中的一个漏洞）的搜索。
