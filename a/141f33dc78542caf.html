云原生 harness 能让 agent 在桌面之外可靠运行吗？

Latent Space · 评分 8/10：K8s 创始人谈 agent harness 云端化，深度长文
原标题：Can a Cloud-Native Harness Make Agents Reliable Beyond the Desktop?

要点

  • Kubernetes 两位创造者 Craig McLuckie 和 Joe Beda 创办的 Stacklok 转向 agent 基础设施
  • Stacklok 推出开源云原生 harness 项目 Mecatl，将 agent loop 与执行环境解耦
  • Stacklok 此前已推出管理 MCP server 的开源平台 ToolHive

从宏观上看，编码 agent 有一个基本架构：LLM 在循环中调用工具，同时携带所需的上下文。由于这在本地最容易实现，许多编码 agent 最初都是终端工具，后来才发展为桌面应用（Claude Code 最初就是一个著名的 CLI 工具）。但正如打开笔记本电脑的梗所表明的那样，现代 agent harness 如果无法在云端管理，就会受到令人沮丧的限制。

自 2025 年以来，OpenAI 和 Anthropic 都在尝试将它们的 harness 更多地转向云端——但成功程度各不相同。挑战包括保持会话可靠、隔离工具执行以及保留上下文。

这听起来很像2010 年代初的容器编排，由此在 2014 年诞生了开源项目 Kubernetes。由 Google 开发的 Kubernetes 成为大规模部署和管理云应用的主导开源系统——它开启了计算的“云原生”时代。

Kubernetes 使用控制循环来保持应用运行、从故障中恢复并在需要时扩展。如果编码 agent 能以同样的方式管理呢？

这正是两位 Kubernetes 创造者 Craig McLuckie 和 Joe Beda 在 Stacklok 上所下的赌注。

Stacklok 曾在 2023 年从 Accel、Madrona 和 Bain Capital 处筹集了 1750 万美元的 A 轮融资。该公司最初专注于软件供应链安全，最近转向基于 Kubernetes 的 agentic 解决方案。

Mecatl：为云构建的 harness

Stacklok 最有趣的产品是 Mecatl，这是一个“云原生 harness”，于 6 月作为GitHub 上的开源项目启动。起初，我以为这个名字读作“me-cattle”——一个双关语，指 Kubernetes 的“牛与宠物”概念，即把服务器、pod 和集群当作牛而不是宠物来对待。但不对，这个名字实际上读作“MEH-kah-tl”，是一个阿兹特克词，意为绳索或绳子！

无论如何，在 harness 的语境下，云原生意味着什么？

McLuckie 说，这主要是关于“将价值中心从桌面转移到云端”。他从企业角度谈论“价值”——代码和上下文通常来自本地环境。“知识产权就在那里，”Beda 插话道。“而如果你真的想将其纳入管理，当它位于桌面上时，难度要大得多。”

McLuckie 补充说，云原生方法还让 Stacklok 能够就 agentic 编码提出一些更深层次的问题。

“为什么 agent 循环与工具调用子系统如此紧密地耦合？为什么 agent 身份要通过人类身份系统的视角来考量？”

在开源 agent harness 方面，已经有备受推崇的解决方案——例如 Pi，一个“极简 agent harness”，Flue 等项目已在其之上构建。我们问 Stacklok 的两位，他们的 harness 有何不同？

Beda 没有具体提到 Pi，但他确实说过，在桌面优先的 harness 中，循环、本地执行和会话状态通常始于同一个进程。

“这个领域有大量的解决方案，但它们基本上都专注于在桌面上运行，”他说。“所以即使它们具有可插拔性，架构仍然是一个进程，或一组紧密耦合的进程，专为在桌面上运行而构建。”

但企业难道不能使用虚拟机、容器或众多不同的沙箱产品之一，将他们的 harness 迁移到云端吗？

Beda 表示，这种“直接迁移”的方法往往会在 agent 的生命周期或使其静默（在等待人工输入时安全暂停）方面产生问题。

“我们的想法是，如果我们从头重新思考 harness，让它真正在云端运行，会怎么样？”

将 agent 循环与执行分离

Mecatl 的一个有趣方法是，它使 agent 循环独立于客户端、模型提供商、状态存储和执行环境。

“这是一个我们知道如何在云端良好运行的应用程序，”Beda 在谈到循环应用程序时说。“如果我们把它拿出来，将其与更敏感的操作（如工具调用和 bash）分离，然后再分离出会话管理和内存等东西，这样这些东西就不再作为 JSONL 文件存储在磁盘上，而是可以原生地放入可管理的系统中”

很多读者可能拥有非常有主见的 harness，根据自己的需求定制。但 Mecatl 的设计超越了单用户、本地 harness，成为企业可以集中运营的基础设施。Beda 将其比作企业管理电子邮件的方式。

“我们认为，未来你在为企业工作时与 agent 的交互属于该企业；他们会希望像管理电子邮件一样管理和治理这些交互。”

将 AI agent 与前沿实验室解耦

Stacklok 的主要动机之一是帮助大型企业减少对前沿实验室和超大规模云服务商的依赖，例如 Codex、Claude Code 和 GitHub Copilot。McLuckie 认为，这类似于 Kubernetes 如何帮助企业减少对大型云提供商的依赖。

对于 McLuckie 来说，“云原生”一词代表了一种“在与云提供商的具体细节解耦的云中运行”的方式。因此，我们在 Stacklok 尝试做的很多事情，或多或少就是我们在 Kubernetes 时代所做的。”

在转向 agent 基础设施后，Stacklok 构建了 ToolHive——一个用于运行和治理 MCP 服务器的开源平台。它最初是为了管理在桌面 Docker 容器中运行的 MCP 服务器。然后，Beda 说，他们将其扩展为一个“基于 Kubernetes 的网关和其他相关服务——一个注册表和一个操作器助手，用于运行和管理 MCP 服务器，并正确处理这些事物的输入输出认证问题。”

正如 McLuckie 所说，这个想法是为了让已经在 Kubernetes 上运行的企业能够“开始将 agent 工作负载带入这些环境”。

Beda 声称，许多其他 agent 工具是为个人或小型初创团队设计的，这对于企业级公司来说行不通。

“我们与规模较大的组织交流时，他们正面临这样的困境：如何将原本为六人团队打造的东西，部署到成千上万人的工程团队中。”

Stacklok 的 LLM 网关

MCP 是第一步。下一步是构建 LLM 网关，在 Stacklok 网站上被称为“AI Gateway”，旨在帮助企业控制访问和成本。

“我们的大多数客户是银行、半导体公司、电信运营商……你知道，都是在相对受监管行业运营的企业，”McLuckie 说。

AI Gateway 是 Stacklok 尚未开源的主要产品，但 Beda 表示它“在我们的路线图上，我们很快就会实现。”

与 Glean 的解决方案不同，Stacklok 的 AI Gateway 目前不会根据任务选择模型。相反，它专注于访问控制、预算、报告和提供商路由。

“我们更倾向于让语义路由模型选择发生在一个在 harness 中打磨过的智能系统里，因为那里有更多的上下文，”McLuckie 解释道。

企业脊柱

既然 ToolHive（MCP 平台）和 Mecatl（harness）都是开源的，Stacklok 的商业模式是什么？

McLuckie 回答说，ToolHive 和 Mecatl 都旨在独立发挥作用，但公司提供跨开源部分的一致身份、授权、策略和审计等功能。

“我们的商业产品是企业脊柱，即将它们全部连接在一起的控制平面，”他说。

“开源项目对于小团队来说相对容易启动和运行，”Beda 补充道。“但一旦你开始将这些扩展到多个集群、多个云，[...] 各种新问题就会涌现。而这正是我们专注于解决的。”

AI 的云原生时代？

亚马逊在 2006 年推出了 S3 和 EC2——云时代的开端——但起初这些产品主要被初创公司和个人使用。几年后，像 Windows Azure 这样的企业级解决方案才出现，然后在 2014 年，Kubernetes 问世，用于大规模管理容器化应用。

我们开始看到同样的模式在 agent 技术中上演。企业不一定希望允许员工自定义开源 harness，甚至不希望他们使用在个人电脑上运行的前沿实验室 harness。Stacklok——由两位云原生领域的王者打造——旨在通过将 agent harness 完全带入云端来解决这些问题。
