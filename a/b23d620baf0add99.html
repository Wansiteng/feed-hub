用 LFM2.5-VL-DSpark 加速视觉语言模型

评分 6/10：视觉语言模型加速技术，有一定工程参考价值
原标题：Accelerating vision-language models with LFM2.5-VL-DSpark

要点

  • Liquid AI 发布 LFM2.5-VL-DSpark 草稿模型，为 LFM2.5-VL-3B 加速
  • 设备端解码最高提速 3.13x，H100 上最高 2.66x，端到端最高 2.62x
  • 草稿模型仅增加 280M 参数，占目标模型 8.9%

今天，我们发布了一款实验性的

DSpark 草稿模型，用于我们的视觉语言模型（VLM）LFM2.5-VL-3B。与我们近期发布的 LFM2.5-DSpark 草稿模型一样，它增加了一条投机解码路径，以极小的内存开销换取更大的速度提升，同时不改变输出质量。

  • 更快的推理：设备端解码速度最高提升 3.13 倍，H100 上最高提升 2.66 倍，端到端增益最高分别达 2.62 倍和 2.27 倍。
  • 内存开销小：草稿模型增加 280M 参数，在 3B 目标模型基础上仅增加 8.9%
  • 首日支持：兼容 LFM 的 DSpark 集成，支持 llama.cpp、MLX-VLM 和 SGLang

VLM 的投机解码如何工作

视觉草稿模型采用与我们文本 LFM2.5-DSpark 草稿模型相同的架构：它在固定的一组抽取层上捕获目标模型的隐藏状态，并以此为依据草拟一个包含 k 个候选 token 的块。图像 patch 和文本 token 在这些层之前被投影到共享表示中，因此无论输入模态如何，草稿模型处理的都是维度相同的隐藏状态向量。推理算法因此与文本模型保持一致。

训练与架构

我们遵循 DSpark 配方，使用混合的视觉语言 SFT 数据，并偏向我们预期模型将服务的工作负载。基于 3、4、5 层的消融实验，草稿模型是一个简化的纯注意力草稿器，具有 4 层和 9 的块大小。我们在最终数据混合上运行了 10 个 epoch，并在每个 epoch 后测量接受率，接受率随着训练 token 增加而提升，随后达到收益递减。在推理时，我们建议根据硬件选择 8 或 9 的块大小。

由此得到的草稿模型约有 280M 参数，仅使部署模型的参数量增加 8.9%。

  • 解码器堆栈（4 层）
    LFM2.5-VL-3B：193.0M
  • 隐藏状态投影
    LFM2.5-VL-3B：21.0M
  • Markov 头
    LFM2.5-VL-3B：65.5M
  • 归一化 + 置信度头
    LFM2.5-VL-3B：6.4k
  • 总计
    LFM2.5-VL-3B：279.5M

CPU 和 GPU 上的推理加速

用于 LFM2.5-VL-3B 的 DSpark 草稿模型首日即支持 llama.cpp、MLX-VLM 和 SGLang。

我们同时测量了设备端推理和 GPU 推理。两种配置均使用 DSpark 块大小 8，并在六项多样化的视觉任务上进行评估，包括通用 VQA、文本 VQA、图像描述、图表 VQA、复杂推理和多轮对话，遵循 MMSpec benchmark。

设备端推理。在 M5 Max 上使用 MLX，解码速度按任务提升 2.30 倍至 3.13 倍。端到端延迟改善 1.56 倍至 2.62 倍。在 M3 Ultra 上使用 llama.cpp，解码提升 1.57 倍至 2.14 倍，端到端提升 1.30 倍至 1.77 倍。

GPU 推理。在 H100 上，同一草稿模型实现 20.4 倍至 2.66 倍的解码加速，端到端改善 1.64 倍至 2.27 倍。

视觉工作负载中投机解码的局限性

在 LLM 中，prefill 主要是计算受限的，其开销随 prompt 长度呈（次）二次增长。VLM 更是雪上加霜，因为图像先经过视觉编码器，然后语言主干网络再处理数百个视觉 token 以及文本 prompt。边缘设备的算力远低于数据中心 GPU，因此 prefill 在端到端延迟中占比更高，正如在 Apple silicon 和 H100 上测得的首 token 时间和 decode 数据所示。（M5 的每核心 GPU 神经加速器缩小了这一差距）。

投机解码只能加速 decode，无法加速视觉编码或 prefill。当这些阶段已经占据了大部分实际耗时，即使 decode 大幅提速，端到端收益也相当有限。这就是阿姆达尔定律：整体加速比受限于工作负载中未被加速的部分。

如何使用 LFM2.5-VL-DSpark

使用 SGLang 运行 DSpark 草稿模型，需要支持 LFM2 目标 DSpark 的 SGLang 构建版本（PR #40651）。启动目标模型时挂载草稿模型：

python -m sglang.launch_server \
  --model-path LiquidAI/LFM2.5-VL-3B \
  --speculative-algorithm DSPARK \
  --speculative-draft-model-path LiquidAI/LFM2.5-VL-3B-DSpark \
  --speculative-draft-attention-backend flashinfer \
  --speculative-dspark-block-size 9 \
  --disable-radix-cache

然后查询位于 http://localhost:30000/v1 的 OpenAI 兼容端点。block size 从草稿模型的 config.json 中读取；基线就是去掉三个 --speculative-* 标志后的同一命令。

使用 llama.cpp 运行它们需要相应的 llama.cpp 构建版本（PR#29339）。

llama-server -m models/LFM2.5-VL-3B-F16.gguf \
  --mmproj models/mmproj-LFM2.5-VL-3B-F16.gguf \
  -md LFM2.5-2.6B-DSpark-F16.gguf \
  --spec-type draft-dspark --spec-draft-n-max 8 --spec-draft-n-min 0 \
  -fa on -ngl 99 -c 8192

使用 MLX-VLM 运行它们需要相应的构建版本（PR#2280）。

mlx_vlm.server --model LiquidAI/LFM2.5-VL-3B --draft-model LiquidAI/LFM2.5-VL-3B-DSpark

block size 从 sidecar 元数据中读取（n-max 会被钳制到该值）。投机解码是精确的：目标模型会验证每一个候选 token，因此贪心输出与单独运行目标模型一致；每次响应的 timings 会报告 draft_n / draft_n_accepted。
